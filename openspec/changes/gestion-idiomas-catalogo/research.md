## 2. Questions (selected intent — retained and answered here)

### Lane 1 — Content language vs UI locale, and the default-language pointer

How established systems model **authored multilingual content** distinct from the **visitor's UI locale**. Per system: where the default/source language is declared; whether changing the default requires moving data; how a **missing** translation resolves; whether the fallback is a configurable pointer or a hard-coded source language.

### Lane 2 — Multi-language export/import shape

(1) Column-naming convention for multilingual product content (locale-suffixed columns, per-locale files, one row per locale). (2) How a **partial** set of translations is imported (missing columns, empty cells, adding a language later). (3) Established behaviour when a translation is **cleared** — delete the row or store an empty value.

### Lane 3 — Language-agnostic product search

Do these systems search across all languages by default, or only the active locale? Cite concrete behaviour and, where possible, the query strategy (translation-table joins vs search index).

## 4. Lane-by-lane findings

### Lane 1 — Content language vs UI locale, and the default-language pointer

**L1.1 — The two concerns are separated explicitly in mature systems.** Pimcore states it directly: `Content localization and UI localization are configured independently, so the languages available for your content can differ from the language used in Pimcore Studio.` (S25). Akeneo has a "PIM default language" that is purely the interface language (`The PIM interface language`, per-user overridable) (S30), while the *content* dimensions are channel + locale (S20, S21). WPML makes the same split for the WordPress admin (`The default language is normally also the admin language. However, you can also choose to display your site's WordPress admin in a different language than the default language of your site's content.`, S11). → **Supports** the ticket's premise that the visitor/UI locale is not the authored-content language (the plugin keeps UI es/en i18n separate from description content).

**L1.2 — Where the default/source language is declared.** Three different placements exist, and none of them is the legacy data column:

- **Config/global pointer**: PrestaShop keeps `Configuration::get('PS_LANG_DEFAULT')` and resolves every language-less lookup through it (S5); Pimcore keeps `Default language - the system-wide fallback locale` plus a per-language `Fallback language` in system settings (S24); Sylius keeps a per-instance `fallbackLocale` set through `setFallbackLocale()` (S18).
- **Content-attached original**: WPML welds the default to the language the content was *created* in (`the language you start in becomes the "original" for all your content – permanently`, S9); Polylang stores a language term per post and a translation group, with `pll_default_language()` as the site-level default (S13, S15).
- **Hard-coded source language**: Odoo hard-codes `en_US` as the base key inside the translated value and as the last element of the fallback chain (S1); Odoo's source strings are always American English (S3).

**L1.3 — Changing the default does not move content data — except where the default is welded to the source.** PrestaShop's default is a configuration value; S5 shows only *resolution* changes when it changes. Pimcore's default is a setting and removing a language explicitly does **not** touch data (S24). Sylius's fallback is a runtime pointer (S18). By contrast WPML documents the failure mode of binding the default to the source: after changing the default, `content that wasn't translated into this language will not show up ... because it doesn't exist in this new default language`, and the recommended remediation is to **duplicate content into the new default language** (S8, S9). → **Supports** D5's model and identifies WPML as the documented counter-example to avoid.

**L1.4 — Missing-translation resolution is a read-time concern, not a stored copy.**
- Odoo compiles reads to `COALESCE(field->>lang, field->>'en_US')` (S1) and the in-memory cache falls back with `vals.get(self._lang, vals.get('en_US', default))` (S1).
- PrestaShop resolves a *missing/invalid language* to `PS_LANG_DEFAULT` (S5: L59, L213, L327-337) — the comment `If $id_lang is invalid (e.g. due to a removed language) $lang_associated is the default language` is direct evidence that default resolution must be **total**.
- Pimcore resolves an empty value through the per-language fallback (S24), traversing inheritance before falling back (S25).
- Sylius **materialises** a new empty translation on read when neither the locale nor the fallback has one (S18) — a write-on-read behaviour that is *not* shared by Odoo/PrestaShop/Pimcore.
- Polylang has **no** content fallback: untranslated content simply does not exist for that language (`if your posts ... are without a language they don't pass the language filter`, S12; switcher falls back to the front page, S14).
- Symfony Translation's fallback chain ends by returning the message id (S26) — the analogous "no value at all" terminal.

**L1.5 — Configurable pointer vs hard-coded source.** Pimcore and Sylius expose explicit, reconfigurable fallback pointers (S24, S18) and Symfony models the fallback as an **ordered chain** (`setFallbackLocales(['en_GB', 'en'])`, S26). Odoo's terminal fallback is the hard-coded source language `en_US` (S1). Both patterns are common; what is absent everywhere is a fallback that points to a **non-language legacy column**.

### Lane 2 — Multi-language export/import shape

**L2.1 — Storage shapes (three families, none is "locale-suffixed columns").**
1. **Sibling row per language**: PrestaShop `_lang` table `(id_object, id_lang, ...translatable fields)` (S4, S5); Akeneo stores one value entry per `locale`+`scope` inside the product's `values` (S23).
2. **Single document with language keys**: Odoo jsonb `{lang: value}` with `en_US` always present (S1, S2).
3. **Separate linked entities**: WPML `Translations are saved in the database as separate products, linked together using WPML's language table.` (S10); Polylang links posts in a translation group (S13).
   → The ticket's `articulo_descripciones` is family **1**, matching PrestaShop and this fork's in-repo precedent.

**L2.2 — Export shape is driven by an explicit locale selection, not by "all languages".** Akeneo requires `one or more locales to export` as a required field of the export profile, defaulting to the channel's activated locales (S22, S21). Odoo's translated content is written back with `en_US` always persisted (S1). No source retrieved defines a normative **locale-suffixed column header** convention for CSV/XLSX; Akeneo's API-level convention is per-value `locale` (S23, non-primary provenance) and Pimcore's CSV import handles locale through a locale-switcher operator or a resolver-level language setting (S27, third party).

**L2.3 — Adding a language later is a normal, non-destructive event.** PrestaShop builds language payloads from `Language::getIDs(false)` — i.e. **all** languages — so a newly added language gets rows on the next object save (S5). Pimcore: `Removing a language ... does not delete its respective data` (S24). Akeneo: locales are activated per channel and then become exportable (S21).

**L2.4 — Partial translations are allowed, but the *absence* is what is displayed as fallback.** WPML: fallback `does not create products in the second language. Instead, it displays the default language content` (S7) — a pure read-time fallback. Polylang: `It is not mandatory to translate all the content.` (S13). Akeneo: values are written `only for the working Locale` (S20), so an untouched locale stays empty.

**L2.5 — Clear semantics (Lane 2, question 3) — answered from source.**
- **PrestaShop does not delete the `_lang` row on clear.** `ObjectModel::update()` does `SELECT COUNT(*) ... WHERE id = X AND id_lang = Y` and then `UPDATE` else `INSERT` (S5). An empty value is written in place; the row disappears only when the *object* is deleted (`delete()` → `DB::delete(... '_lang', primary = id)`, S5). Note also L384-395: for **required** fields PrestaShop *fills* an empty non-default language with the default language's value **on write** (S5) — i.e. it propagates the source text instead of leaving the translation empty.
- **Odoo removes the language key and drops the column to `NULL` when nothing remains.** `LangProxyDict.__delitem__` → `vals.pop(self._lang, None)`; `get_column_update` → `return PsycopgJson(value) if value else None` (S1). Reads then fall through `COALESCE(...)` to `en_US` (S1).
  → Both implementations agree that a *cleared* translation is represented by **absence/emptiness for that language**, and the fallback — not a copy stored in that language's slot — supplies the visible text. PrestaShop's required-field write-through (S5) is the one divergence, and it exists to keep required fields non-empty.

### Lane 3 — Language-agnostic product search

**L3.1 — The established default is locale-scoped search, not cross-language search.**
- PrestaShop's index is language-typed: `ps_search_word{ id_word, id_shop, id_lang, word }` (S6) — a word belongs to a language, so a Spanish query cannot match an English-only word.
- Akeneo: `The search only covers the Attributes for the Locale and Channel you currently have selected ... switch Locale or Channel to search other translations` (S20).
- Odoo: translated-field conditions compile to `COALESCE(field->>lang, field->>'en_US')` (S1) — current language first, then the source language; not a union over languages.
- Magento: search terms/synonyms are `scoped per Store View` (S28, community mirror) and fulltext documents are indexed under a store-scoped index `magento2_<entity>_<store_id>_v<n>` (S29, third party).
- → **No source retrieved shows a system that searches across all languages by default.** D11 is therefore a deliberate deviation, not an industry default.

**L3.2 — Query strategy where a system does span languages.** The only cross-language-ish mechanism observed is the **fallback COALESCE** (Odoo, S1): it broadens a *single* language query to include the source language, not the whole translation set. The in-repo `tarif_articulo::search_tarifario` `LEFT JOIN articulo_descripciones` + `OR` pattern (recorded in `explore.md`) has no external equivalent in the retrieved sources.

## 6. Analysis against the confirmed decisions D1–D12

Verdicts: **supports** = admitted evidence is consistent with the decision; **contradicts** = admitted evidence points the other way; **partial** = evidence bears on part of the decision only; **not addressed** = no admitted evidence (external sources do not decide product-local choices).

With D1, `articulos.descripcion` can only go stale; it can never gain the default language's newest text. The read chain must therefore treat it as a legacy terminal, not as a live default. |
| **D2** | Single description/short-description pair driven by a language selector in `ventas_articulo` | **supports** | Every system with authored content exposes a working-context selector: Akeneo `Select your working context (Channel/Locale)` with `values are saved only for the working Locale` (S20); Pimcore's language switcher in the editor (S25); PrestaShop's `id_lang` object context (S4, S5). ### 6.1 Where the evidence contradicts or cautions against a confirmed decision

1. **D11 is a deviation from every retrieved system** (S1, S6, S20, S28/S29). Keep it, but document it as deliberate and justify it from the frozen-column constraint, not from precedent.
2. **D1 removes the source-language write-through that PrestaShop and Odoo rely on** (S5, S1). Consequence: `articulos.descripcion` must never be presented as an equivalent of the default language; if it is, users will see stale text indefinitely.
3. **D5 is contradicted by WPML's model** (S8, S9) — which is precisely why D5 keeps the pointer separate from the data. WPML is the counter-example that validates D5, not a competing design.
4. **D6's third leg (the legacy column) has no external equivalent.** It is a compatibility shim, not an established pattern; the spec should mark it deprecated.
5. **D2 + D8 interact**: Akeneo writes `only for the working Locale` (S20), so an editor who switches language must not accidentally write the other language's text. The current defect (g) does exactly that for the default language (writing `$art->descripcion` over the posted value) — D2 fixes it, and the fix must be asserted by test.

## 7. Concrete recommendations for `spec` / `design`

Each recommendation is tied to the sources above.

**R1 — Default-pointer model (spec).** Keep `catalogo_idiomas.por_defecto` as the single pointer, and make resolution **total**: exactly one *active* default must always resolve, and an unresolvable default must degrade deterministically instead of returning `false`. Evidence: PrestaShop treats an invalid language as "use the default" and documents it as an invariant (S5, L59/L213/L327-337); Pimcore defines `Default language` as `the system-wide fallback locale` (S24). Do **not** bind the default to `articulos.descripcion` — WPML is the documented failure mode (S8, S9).

**R2 — Do not materialise fallbacks on write or on read.** A translation is present or absent; the fallback is resolved at read time. Evidence: Odoo writes/reads per language and falls back in SQL (S1); Pimcore returns the fallback value rather than copying it (S24); WPML's fallback `does not create products in the second language` (S7). Explicitly avoid Sylius's write-on-read materialisation (S18). Consequence: remove `set_descripcion_idioma()`'s mirror branch (explore §2.2) and never let `saveMultiidiomaDescriptions()` copy `$art->descripcion` into a language slot (defect g).

**R3 — Clearing rule (spec): an empty description for a language deletes that language's row.** Evidence: PrestaShop stores emptiness by updating the `_lang` row in place (S5) and Odoo removes the language key, nulling the column only when nothing remains (S1) — both treat a cleared translation as *absence for that language*, and the visible text then comes from the fallback. Practical shape: allow `articulo_descripcion::test()` to accept an empty `descripcion`, and have the save path delete the row when both `descripcion` and `descripcion_corta` are empty (keep the row when only `descripcion_corta` is set). **This "keep the row if `descripcion_corta` is set" rule has no external evidence — mark it as a local decision in the spec.**

**R4 — Export header naming and ordering (spec).** Keep the locked base headers untouched and append locale columns additively, using the fork's existing suffix convention (`descripcion_<codidioma>`, `descripcion_corta_<codidioma>`) with a deterministic order (default language first, then the remaining active languages ordered by `codidioma`). Evidence for *per-locale export*: Akeneo's export requires an explicit locale selection (S22). Evidence that the *suffix shape itself* is not a standard: PrestaShop and Odoo use language-keyed containers, not suffixed headers (S4, S1). Spec must define: (a) deactivated languages are omitted from new exports; (b) unknown/removed locale columns in an imported file are **ignored** (not an error, not a silent language creation); (c) imports never create or modify the language registry.

**R5 — Import must target an explicit language (spec/design).** Akeneo edits and imports happen inside a `working context` and values are `saved only for the working Locale` (S20). Therefore the `catalogo_core` import wizard should take a target language (defaulting to the configured default) instead of relying on an implicit default, closing the D10 ambiguity for writes. Evidence: S20; supporting context: Akeneo channel locale selection (S21) and export locale selection (S22).

**R6 — Search strategy (design).** Implement D11 as a single, isolated predicate in `ArticuloSearchQueryBuilder`: base column `OR` a join over `articulo_descripciones`, and invalidate `articulos_search_*` on **every** description write (including non-default languages, which today invalidate nothing — explore defect f). Document the deviation: every retrieved system searches per locale/store view (S6, S20, S1, S28, S29). Add tests that prove a non-default-language term is findable and that a cleared translation stops matching.

**R7 — Language deletion and orphans (design).** Two evidence-backed options, choose explicitly: (a) application-level cleanup in `catalogo_idioma::delete()` — PrestaShop deletes child `_lang` rows in `ObjectModel::delete()` rather than relying on a DB FK (S5); or (b) a DB FK with `ON DELETE CASCADE`, which is the DB-level equivalent. Pimcore's precedent is the opposite direction — removal **keeps** data and exposes a cleanup command (S24) — so the design must state the chosen semantics and, if a migration is added, must be idempotent.

**R8 — "Last language" / "default cannot be inactive" invariants are local.** No retrieved system models an inactive default or a minimum language count. Mark these as product invariants in the spec (they follow from R1's totality requirement) rather than citing precedent. The *need* for R1 is evidence-backed; the specific guard rules are not.

**R9 — UI locale stays untouched.** The plugin's UI i18n (Symfony Translation, es/en) is a separate concern from description content, exactly as Pimcore and Akeneo model it (S25, S30) and as WPML models admin language vs content language (S11). Symfony's own fallback chain for UI strings (S26) should not be conflated with the description read chain.

## 8. Contradictions, uncertainty, freshness

**Contradictions found (admitted evidence vs. confirmed decisions):**

- **D11 vs. locale-scoped search** — the only decision the evidence actively contradicts; the deviation is deliberate and must be documented (§6.1, R6).
- **D1 vs. source-language write-through** — PrestaShop fills empty required translations from the default on write (S5) and Odoo always persists `en_US` (S1); D1 forbids the equivalent here. Not a contradiction of intent, but a real loss of a safety net.
- **PrestaShop's `formatFields()` write-through (S5) vs. "absence = fallback" (R2/R3)** — for required fields PrestaShop stores the fallback text in the language slot. The ticket should choose absence, and its spec should say so explicitly, because the opposite choice is what heroed defect (g).

**Uncertainty (stated, not hidden):**

- PrestaShop's **front-office/read** fallback for an empty (but existing) `_lang` value was **not** verified; only the write path (`formatFields`) and the invalid-language resolution (`getAssociatedLanguage`) were read from source (S5).
- Odoo's `ir.default` as a jsonb fallback (S2) comes from a search snippet; the page was not fetched.
- Magento's product-attribute inheritance for missing store-view values is inferred from the configuration-scope model (S16, S17) plus two non-primary sources (S28, S29). No Adobe developer page on product-attribute fallback was retrieved.
- Akeneo's CSV **header** naming for localizable attributes was not retrieved from an Akeneo-published source; the only naming evidence observed is a third-party connector's `{code}~{locale}` convention (not cited as a source because it is a vendor's integration doc, not Akeneo's).
- Pimcore's "one file per language" behaviour was not confirmed; the retrieved Pimcore material covers locale selection (S27, non-primary) and fallback configuration (S24).
- PrestaShop's and WPML's translations storage claims are at the *documented* level (S4, S10), not read from schema definitions.

**Freshness.** All sources were accessed 2026-09-22. Version anchors observed: PrestaShop `develop` source + v8 docs (S4), PrestaShop 8 search-index docs (S6), Odoo 19.0 source (S1) and 19.0 docs snippet (S2), WPML pages updated 2023-09-08 → 2026-03-06 (S7–S11), Polylang pages 2024-04-26 → 2026-06-25 (S12–S15), Adobe pages 2023-11-29 → 2026-08-20 (S16, S17), Sylius `/sylius/Resource` `master` (S18, an older-line component: `getTranslation()` here has no `$fallback` boolean parameter, which exists in newer Sylius releases — the *direction* of the behaviour is stable, the exact signature may differ), Akeneo v7/Serenity help (S20–S22, S30), Pimcore 2026.2 (S24, S25), Symfony Translation 8.2 autodocs (S26).

**Potential staleness risk.** Sylius/Resource `master` is the standalone component repository, which is not necessarily what current Sylius applications use (the trait has since moved into `Sylius/Sylius`). Treat S18 as directional evidence for "configurable fallback pointer + optional materialisation", and prefer Symfony/S18-agnostic framing in the design.
